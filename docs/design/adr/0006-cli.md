# 0006. 提供独立 CLI 模块

- Status: Accepted
- Date: 2026-11-01

## Context

KnitID 是 Java 库，主要使用方式是 Spring Boot 或直接调用 Java API。但生成/解析 ID 也经常发生在
终端、脚本、日志排障和 CI 场景中：

- 从日志里取一个 KSID/BIZ ID 反解时间戳、节点、序列；
- 为测试数据或 SQL 脚本生成固定类型的 ID；
- 不启动 Spring Boot 验证某个 ID 的类型和元数据；
- 运维/测试人员不写 Java 代码。

这些场景不需要 Redis、数据库或 WorkerId 租约，只需要本地、可重复的生成/解析能力。

## Decision

新增独立模块 `knitid-cli`，作为普通 Java 应用发布，不依赖 Spring：

- 命令：`gen`、`parse`、`help`、`version`；
- v1 类型：
  - 生成：UUID7、UUID8、ULID、KSUID、TypeID；
  - 解析：UUID7、UUID8、ULID、KSUID、TypeID、纯数字 KSID；
- 输出：文本或 JSON；
- 打包为带依赖的可执行 JAR（`java -jar`）；
- 不引入 picocli/Spring Shell 等额外 CLI 框架，保持依赖最小；
- 不访问网络，不读取隐式配置，不包含 secret。

## Consequences

- CLI 是独立 artifact，不改变 `knitid-core` 的零 Spring 约束；
- 普通 `mvn verify` 会编译/测试 CLI，但业务应用不会传递依赖它；
- v1 不覆盖 BIZ、KSID 完整位布局、Redis/DB 序列、WorkerId 分配和 daemon 模式；
- 这些能力继续通过 Java/Spring API 使用，CLI 后续按用户反馈扩展；
- 需要维护命令参数、JSON 输出契约、退出码和打包/文档。

## Alternatives

- **Spring Shell**：能力强但引入 Spring 运行时，不符合 CLI 的轻量目标；
- **picocli**：成熟，但 v1 命令很简单，额外依赖收益不足；
- **只在文档给 JShell/Java 片段**：门槛仍高，不适合非 Java 用户；
- **把 CLI 放进 samples**：会污染示例模块，也不利于独立发布。
